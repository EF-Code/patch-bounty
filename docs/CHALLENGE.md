# Synthetic account authorization challenge v1

This local challenge uses only the checked-in Python fixtures. A candidate is a JSON object with exactly `user` and `path`. Each account name is 1–32 lowercase ASCII letters, digits or hyphens, beginning with a letter; `path` must be `/accounts/<account>/profile`. The input is limited to 4096 bytes, and duplicate keys are invalid. No submitted code is executed.

The vulnerable revision checks a raw path prefix. The incomplete revision checks the route but still accepts an account name beginning with the user's name. The corrected revision compares the complete account component. A candidate is **eligible** only when the target account differs from the user, the vulnerable and incomplete revisions both return `allowed: true`, and the corrected revision returns `allowed: false`. Malformed input, a fixture integrity mismatch, sandbox failure, timeout, or unexpected output is an error, never a qualifying result.

The verifier pins each fixture's SHA-256 in its source and runs a private copy of the verified bytes. Successful results contain the raw input and canonical candidate digests, fixture digests, verifier source digest, Python executable digest and version, per-revision standard output, standard error and exit code. Error results identify the input (or its first 4097 bytes when oversized), verifier, pinned fixtures and any available partial execution output. Canonical JSON uses sorted keys, ASCII escaping and compact separators. The evidence is local and unsigned; its hashes identify bytes, not their correctness or provenance. It does not fully pin the Python standard library, OS libraries, Bubblewrap version, kernel, or runtime configuration, and it is not an execution attestation. Retain the actual candidate and verifier source alongside the JSON if evidence is needed later. The verifier does not send a payout or prove that a verifier assertion is honest.

The sandbox is intentionally limited to this fixture and treats candidate JSON as data. Bubblewrap uses separate user, network, PID and other namespaces, a cleared environment, read-only system/runtime mounts, an ephemeral `/tmp`, and no home directory mount. Resource limits and a wall-clock timeout bound execution. System library and runtime mounts expose their contents to the fixture, so those paths must not contain credentials. Bubblewrap and these limits should not be represented as a complete isolation boundary for arbitrary hostile programs. Use an appropriately hardened, separately managed sandbox before broadening the input or fixture model.
